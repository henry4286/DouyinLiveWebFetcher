# DouyinLiveWebFetcher 短期接入与改造分析

更新日期：2026-09-04

## 1. 决策与边界

直播话术副驾的核心需求是分析直播间自然评论及其他动态，为主播提供实时话术建议，并允许主播从话术库主动选择分类。直播间数据获取只是可替换的基础设施，不是产品核心。

当前弹幕小玩法正式环境只能提供命中预配置指令的评论，不能满足全量自然评论分析需求；直播互动插件的新应用准入又处于关闭状态。因此，本仓库被选为短期技术验证用的数据采集候选适配器。目标架构必须保证：

1. 本仓库只负责连接网页直播间、解码平台消息并输出结构化采集事件。
2. `E:\projects\douyin` 负责主播绑定、场次管理、去重入箱、意图识别、话术选择、安全控制、展示和审计。
3. 两个项目只通过有版本的事件契约连接，不共享抓取器内部类、Cookie、签名或 Protobuf 对象。
4. 将来官方直播互动插件恢复准入时，只替换事件来源适配器，不修改话术核心。

```text
抖音网页直播间（短期、非官方协议）
              │
              ▼
DouyinLiveWebFetcher
连接 / 解包 / 最小字段提取
              │ CollectorEvent v1
              ▼
有界传输通道（首选本机 NDJSON/IPC，后续可换受控 HTTP）
              │
              ▼
douyin 项目的 WebFetcherLiveEventSource
校验 / 映射 / 场次绑定 / NormalizedLiveEvent
              │
              ▼
LiveEventIngressCoordinator → LiveCopilotService
```

独立进程是为了故障隔离、Python/Node 运行时隔离和便于替换，并不构成许可证结论。

## 2. 当前实现与实测结论

### 2.1 当前执行流

`main.py` 创建 `DouyinLiveWebFetcher` 后调用 `start()`。`liveMan.py` 随后：

1. 请求网页版直播间，取得 `ttwid` 和真实 `room_id`；
2. 计算签名并建立 WebSocket；
3. 启动心跳线程，处理 ACK；
4. 用本地 Protobuf 模型解包消息；
5. 在 `--output ndjson` 模式把已支持的消息转换为 `CollectorEvent v1`，stdout 每行只输出一个事件，诊断写入 stderr；默认 `human` 模式仍保留原有中文控制台输出。

### 2.2 2026-09-04 本地观察

使用直播间 `957390047296` 连续观察约 4 分钟，结果只代表该次技术验证，不是可用性承诺或容量基准：

- WebSocket 成功建立，心跳持续发送，观察窗口内未出现断线；
- 能收到未要求预配置指令的自然评论，中文、表情和 `@` 内容可以解析；
- 同时观察到进场、点赞、关注、粉丝团、在线人数和排行榜等消息；
- 在约 1.2 万在线观众的直播间中进程保持运行，观察到的 Python 进程内存约 63.2 MB，CPU 占用较低；
- 观察窗口内没有完成断线重连、长时间内存增长、重复率、丢失率或直播结束行为验证。

已发现的正确性问题：

- 实测用户 ID 均显示为 `111111`，在字段语义和解析结构校正前不能用于用户识别、聚合、幂等或画像；
- 部分粉丝团消息 `content` 为空，说明当前字段提取不完整；
- 排行榜处理会打印巨大对象，长期运行会污染日志并放大 I/O；
- 当前观察无法证明“平台全量、零丢失、严格有序”。只能确认收到了普通自然评论的数据形态。

## 3. 第一阶段进度与仍未解除的上线阻断

| 问题 | 当前状态 | 影响/下一步 |
|---|---|---|
| 输出契约 | 已实现 `CollectorEvent v1` callback 和 NDJSON sink；human 模式保留 | 主项目已用独立监管器消费 NDJSON，严禁重新解析中文日志 |
| 异常处理 | 信封、ACK 和消息解析错误已分类并写入生命周期/诊断输出 | 还需错误计数、限速和告警，避免高频错误淹没 stderr |

## 4. CollectorEvent v1 契约

采集仓库输出来源层事件，主项目适配器负责把它转换为已有的 `NormalizedLiveEvent`。推荐 NDJSON：一行一个完整 JSON，不把普通日志混入 stdout；诊断日志统一写 stderr。

```json
{
  "schemaVersion": "douyin-web-collector-event-v1",
  "kind": "data",
  "eventId": "7392094459690748497",
  "roomId": "7392091211001140287",
  "webRid": "957390047296",
  "type": "comment",
  "occurredAt": 1788480000123,
  "receivedAt": 1788480000189,
  "actor": {
    "sourceUserId": null,
    "nickname": "已脱敏或按策略提供"
  },
  "payload": {
    "content": "这套搭配为什么这样选"
  },
  "source": {
    "name": "douyin-web",
    "protocol": "webcast-im",
    "method": "WebcastChatMessage"
  },
  "quality": {
    "eventId": "platform",
    "actorId": "unavailable",
    "occurredAt": "platform"
  }
}
```

字段约束：

- `schemaVersion`：必填，版本不认识时下游必须拒收并报警。
- `kind`：`data` 或 `lifecycle`。只有 `data` 会映射为核心直播事件。
- `eventId`：优先使用消息 `Common.msg_id` 的十进制字符串。不要加入采集器名称，使同一抖音事件未来经官方和网页来源到达时仍有机会使用同一去重键。缺失时使用双方约定的确定性哈希，并在 `quality.eventId=fallback` 标记，不能用随机 UUID。若平台 ID 和可信平台时间同时缺失，哈希中的 `occurredAt` 只能采用本次 `receivedAt`：它对同一次观测是确定的，但稍后重收会得到另一个 ID，不能宣称跨重收去重。
- `roomId`：平台真实房间 ID；`webRid` 是用户输入的网页直播 ID，两者不能混用。
- `occurredAt`：优先平台 `Common.create_time`，统一为 Unix 毫秒；`receivedAt` 是本机接收时间，用于衡量延迟。
- `actor.sourceUserId`：只有验证为稳定、真实且允许处理时才输出。当前 `111111` 必须映射为 `null`，不能伪装成抖音开放平台 `open_id` 或 `sec_open_id`。
- `payload`：只输出该事件必要字段，不透传整个 Protobuf 对象。
- `source` 和 `quality`：用于诊断来源与字段可信度；它们不进入话术业务判断。

建议的数据类型映射：

| WebSocket method | CollectorEvent `type` | 核心类型 | 说明 |
|---|---|---|---|
| `WebcastChatMessage` | `comment` | `comment` | `payload.content` 必填 |
| `WebcastLikeMessage` | `like` | `like` | 使用本次增量；不能假定零丢失 |
| `WebcastGiftMessage` | `gift` | `gift` | 包含礼物 ID、名称、数量；连击需专项去重 |
| `WebcastMemberMessage` | `enter_room` | `enter_room` | 高流量时可降级采样或丢弃 |
| `WebcastSocialMessage` | 默认不输出业务事件 | 无 | action 语义未验证；结构化模式只记录不含用户信息的安全诊断，禁止伪称关注 |
| `WebcastFansclubMessage` | `fansclub` | `fansclub` | 当前空 content 不能作为唯一依据 |
| `WebcastRoomUserSeqMessage` / `WebcastRoomStatsMessage` | 默认不输出业务事件 | 无 | 结构化模式只记录安全统计诊断，不承诺精确结算 |
| `WebcastControlMessage` | `room_control` | 生命周期 | status=3 表示直播结束 |
| 排行榜、流适配、未知消息 | 默认不输出业务事件 | 无 | 只计数，按需采样诊断 |

`anchorOpenId` 不应由采集器猜测。主项目必须通过启动配置中的 `anchorBindingId + webRid` 将房间绑定到已登记主播，再填充自己的 `anchorOpenId`。绑定不唯一或主播不存在时，事件进入隔离队列而不是进入话术核心。

## 5. 生命周期和传输

### 5.1 生命周期事件

采集器还应输出独立的控制事件：

- `collector.starting`
- `room.resolved`
- `source.connected`
- `source.disconnected`
- `source.reconnecting`
- `room.ended`
- `collector.stopping`
- `collector.error`

生命周期事件至少携带 `roomId/webRid`、状态发生时间、连接代次 `connectionEpoch`、重连次数和可公开的错误分类。Cookie、完整 URL 查询参数、签名和原始响应不得进入事件。

`start()` 应阻塞到运行循环结束；`stop()` 必须幂等，设置 stop event、关闭 WebSocket、结束心跳、停止重连并清空或限时排空队列。直播结束是正常终态；网络失败和协议失败不是同一状态。

CLI 的父进程控制协议为 opt-in：只有传入 `--control-stdin` 才启动 daemon 控制线程，并且必须在阻塞的 `start()` 之前启动。stdin 每次只做有限长度读取，仅接受单独一行、内容精确为 `stop` 的指令；管道 EOF 与 `stop` 都调用同一个幂等停止路径。未知、空白或超长输入不回显原文，只向 stderr 写安全错误类别，不能污染 stdout NDJSON。采集循环退出时只对控制线程做有超时的短暂 join，不能因 stdin 仍阻塞而拖住进程退出。未启用该参数时保持原 CLI 行为。

### 5.2 重连策略

- 非主动关闭且直播未确认结束时自动重连；
- 指数退避加随机抖动，例如 1、2、4、8、16、30、60 秒，上限 60 秒；
- 稳定连接一段时间后重置退避；
- 每次重连重新解析必要的房间和签名状态，不能无限复用过期字段；
- 连续协议错误触发熔断并报警，避免高频请求；
- `connectionEpoch` 递增，但不能写入 `eventId`。

### 5.3 背压和优先级

WebSocket 回调只做 ACK、解包、最小字段提取和入队。传输使用有界队列：

1. 评论、礼物、关注、粉丝团和直播结束为高优先级；
2. 点赞可按短时间窗合并；
3. 进场和统计可采样或在过载时先丢弃；
4. 排行榜默认不进入业务通道；
5. 队列满时必须计数和报警，不能静默丢弃，也不能因为日志或下游阻塞 WebSocket ACK。

第一阶段推荐本机子进程 stdout NDJSON：部署简单、凭据不跨主机。主项目负责拉起进程、传入经过校验的 `webRid`、读取 stdout、监控退出码和限速重启，并通过启用 `--control-stdin` 后发送 `stop\n` 实现优雅停止；若父进程直接关闭控制管道，EOF 同样要求采集器停止。若改用 HTTP，必须增加本机绑定或 mTLS、认证、请求大小限制、超时和重放防护。

## 6. 去重、顺序和一致性

- 主去重键使用平台消息 ID；主项目的 inbox 建立唯一约束。
- 对缺失平台 ID 的事件，确定性哈希输入必须固定并跨来源统一；降级 ID 只提供有限的重复抑制能力。
- 礼物连击需要用消息 ID、group/combo 字段和结束标志建立状态机，不能简单把每帧 `combo_count` 相加。
- 不承诺严格顺序。下游以 `occurredAt` 做有限窗口排序，超窗事件照常幂等消费并记录迟到。
- 重连后可能重复或缺失；网页协议没有可依赖的正式补偿 SLA，产品不得宣传零丢失。
- 评论是生成话术的重要输入，但不应直接触发不可逆的付费、派奖或权益操作。

## 7. 可观测性和协议漂移

至少提供：

- 状态：当前房间、连接状态、连接代次、最后收到事件时间、最后心跳和 ACK 时间；
- 计数：按 method 收到、解析成功、过滤、队列丢弃、传输成功、传输失败；
- 延迟：平台发生到采集、采集到主项目入箱的分位数；
- 错误：HTTP、签名、房间解析、WebSocket、gzip、Protobuf、字段校验和下游背压分别计数；
- 漂移：未知 method、已知 method 解析失败率、核心字段空值率；
- 资源：CPU、RSS、线程数、队列深度和日志速率。

日志使用结构化字段并限速。排行榜等大对象禁止完整打印。异常日志只保留 method、错误类、经过脱敏的房间标识和采样后的诊断摘要。任何 `except Exception: pass` 都必须改为可计数、可追踪的失败路径。

应准备录制的、去标识化的二进制样本做回归测试；样本必须有合法来源和保留期限，不能把真实评论和昵称直接提交到仓库。每次签名、UA 或 Protobuf 更新都跑兼容性测试和金丝雀房间验证。

## 8. 隐私、凭据与合规门槛

自然评论、昵称、头像、用户标识、关注和礼物行为都可能构成个人信息或用户行为数据。最低要求：

- 授权硬门：仅允许采集已取得主播明确书面授权、且登记在白名单中的指定直播间；授权记录必须明确主体、房间、用途、数据范围、期限和撤回方式。未匹配有效授权时必须拒绝启动，禁止批量枚举直播间、扫描开播状态或采集任何无关房间；
- 撤回处置：主播撤回授权或授权到期后，必须立即停止对应房间的采集和重连，并按既定留存/删除策略删除原始事件、诊断样本及能够关联到该房间的派生数据，保留的数据只能是依法或依约必须保存的最小审计记录；
- 数据最小化：只采集话术生成实际需要的事件，默认关闭排行榜和完整 raw payload；
- 目的限制：不得把话术场景数据自动用于画像、广告、营销名单或其他未告知用途；
- 日志脱敏：默认不打印评论全文、昵称和稳定用户 ID；诊断样本单独授权、加密和到期删除；
- 访问控制：生产与开发凭据、原始事件和聚合结果分权；所有读取有审计；
- 留存：原始评论采用尽可能短的 TTL，话术核心优先保存派生结果和必要审计，不无限保留原文；
- 主体请求与删除：明确房间、主播和用户数据的查找及删除路径；
- 凭据：Cookie、`ttwid`、nonce、signature、完整 WSS URL 只存在采集进程内存中，不进入事件总线、错误上报、截图或配置仓库；
- 安全停止：发现平台要求停止、异常流量、签名失效或疑似风控时，可按房间和全局立即熔断。

本仓库使用未公开网页协议，稳定性、平台条款、反自动化机制和授权边界都与官方开放能力不同。技术上能收到事件不等于获得了生产使用许可。

建议分阶段改造：

## 10. 恢复官方互动插件后的迁移原则

官方入口恢复后，不在核心代码中增加 `if webfetcher / if official` 分支。两种来源都实现主项目的 `LiveEventSource`，由启动配置选择并由 `LiveEventIngressCoordinator` 统一管理。

迁移步骤：

1. 官方适配器先在影子模式输出同一 `NormalizedLiveEvent`；
2. 对比事件类型覆盖率、字段空值、延迟、重复和丢失，不把昵称当主键；
3. 统一平台消息 ID 的生成规则，验证跨来源去重；
4. 小比例房间切到官方主来源，WebFetcher 只做短期影子观察；
5. 验收稳定后停止 WebFetcher，不保留双写常态；
6. 按留存策略清理 Cookie、抓取原始样本和临时数据，并保留必要的迁移审计。

任何官方入口特有的 ACK、任务启停、失败回查和 token 生命周期都封装在官方适配器中；任何 WebFetcher 特有的签名、Cookie、网页 room_id 解析和重连都留在本仓库。话术核心只看到统一事件，因此不因迁移重新开发。
